COMP6452 26T2 Project 2 Task 3 — deployed smart contracts

Hyperledger Fabric has no account address as an account-based ledger such as
Ethereum does. A deployed contract is addressed by the tuple

    channel  ->  chaincode name  ->  contract name  ->  transaction name

and the installed package is separately identified by a package ID, which is a
deterministic SHA-256 hash of the chaincode package. Both are recorded below.

The contract name is part of the address here and not optional: batch-registry
hosts two contracts, so every client call in this project is qualified, e.g.

    contract.evaluateTransaction('BatchQueryContract:GetBatchHistory', batchId)

Everything below was read back from the running network, not from the source:
  peer lifecycle chaincode querycommitted --channelID mychannel
  peer lifecycle chaincode queryapproved  --channelID mychannel --name <name>
  peer version

NOTES

Sequence 4 because the two chaincodes were upgraded three times during
development; sequence 4 is the definition currently committed on mychannel.

A package ID is a content hash of the installed package, so it changes whenever
the chaincode source or its build output changes. Redeploying this archive with
network/scripts/deployAll.sh installs the same three contracts but labels them
batch-registry_1 / coldchain-compliance_1 at version 1, sequence 1, and will
produce package IDs different from the two above. That is expected: the IDs
recorded here identify the deployment this submission was demonstrated on.

To read the current values on any live network:
    peer lifecycle chaincode queryinstalled
    peer lifecycle chaincode querycommitted --channelID mychannel
deployChaincode.sh also prints the package ID it committed, on its last line.
